How it works

How lockfile works

Two sides in two OS accounts. Only the console touches the file.

The source credentials, the plugins, the fetched files and the audit log live in the console account lockfile. The agent side, in your own account, holds none of them and gets 1s and 0s.

Two sides

 agent account (CLI / MCP)            lockfile account (console)
   lockfile plan/run/answers  ──UDS──▶  approve ─▶ fetch ─▶ workspace (0700)
            ▲                   JSON-RPC                       │ fd 3, read-only
            │                                                  ▼
            └────── 1 / 0 per plugin ◀── strict check ◀── sandboxed plugin process
  • The console (lockfile console --profile P) is started by lockhub’s lox with its hub flags, in a container of its own. It serves the profile on a socket in /run/lockfile. Its plans are decided in lox run.
  • The agent side is the lockfile CLI (status, sources, plugins, plan, run, answers, release) and the lockfile mcp server with the same seven tools. It holds no secret, no plugin and no file.

The life of a plan

  1. The agent picks its questions. lockfile plugins lists the installed plugins: each one’s question and what 1 and 0 mean. The agent knows the exact key from you or from a ticket: there is no listing and no stat.

  2. The agent submits a plan. lockfile plan --key K --plugin X --plugin Y, or the lockfile_plan MCP tool.

    The console validates the request alone, without touching the source. The profile exists, the key is under its prefix, every plugin is installed and verified, and the count stays within max_plugins_per_handle.

  3. You approve. The plan becomes a ticket on lockhub: the key as the agent typed it, each plugin with its question, version and marketplace, and how many answers the plan reveals. You answer it in lox run: y approves, n denies.

  4. The console fetches. The file goes into a fresh 0700 workspace in the console account. An object above max_object_bytes is refused while streaming.

    Any fetch failure (missing, too big, denied, network) reaches the agent as one code, fetch_failed. The cause goes to the audit.

  5. Each plugin runs in its own sandbox with the file as a read-only fd 3. It must write exactly 1 or 0 and exit 0. Anything else is plugin_error with result: null.

  6. The answers come back together, at the next multiple of answer_quantum after the run started. The agent gets a handle (f_…) for follow-up questions.

An approved plan runs once, for the peer that asked, within 10 minutes and with the policy unchanged. plan --run asks for approval and runs it in one call.

There is no size, type, hash or path on the screen: no source has been touched yet.

A plugin from an unofficial marketplace adds a red ▲ UNOFFICIAL MARKETPLACE line, and its plan is never auto-approved.

From the agent’s side

# What can I ask?
lockfile plugins --json

# Ask, and wait for the human
lockfile plan --key invoices/2026/10/abc123.pdf \
  --plugin file.non-empty --plugin format.is-pdf --run --json

# One more question on the same file, no refetch
lockfile plan --handle f_8Kq2xR --plugin pdf.parses --run --json

# What was already answered, then delete the fetched file now
lockfile answers f_8Kq2xR --json
lockfile release f_8Kq2xR

Every agent command and lockfile mcp take --instance NAME, to reach one lock among several of this type.

Exit codes depend on the outcome only, never on an answer: 0 answered, 1 no console or error, 2 refused, 3 denied or no answer in time, 64 usage.

Refusals the agent can act on

Every refusal but E_FETCH_FAILED is computed from the request and the local install, before or without reading the file.

Each one carries a stable code, a static hint and a retry rule: rewrite the request, ask the user, or stop.

Refusal codes
CodeRetryMeaning
E_KEY_OUTSIDE_PREFIXrewritethe key is not under the profile’s prefix
E_UNKNOWN_PROFILErewriteno console serves that profile
E_TOO_MANY_PLUGINSrewritethe plan would pass max_plugins_per_handle
E_HANDLE_EXPIREDrewritethe handle expired or was released; plan again with the key
E_PLUGIN_NOT_INSTALLEDask the userthe human must install it
E_PLUGIN_YANKEDask the userthe marketplace withdrew that version
E_PLUGIN_TAMPEREDstopan installed plugin does not match its lock entry (lockfile plugin verify)
E_SANDBOX_UNAVAILABLEstopthe plugin sandbox is unavailable (lockfile doctor)
E_FETCH_FAILEDstopthe key could not be fetched (the cause is in the audit only)

In the console

The console prints each outcome as plan pl_…: answered or refused <code>.

The answers, causes, sizes and hashes go to the audit. Read it with lockfile audit [--since 24h] [--json], in the console account only.

Reach the console with lox attach NAME, then:

  • :review: apply a pending loosening (a plugin installed or a marketplace added while the console runs).
  • :status: the console state.
  • :quit: stop the console; fetched files are deleted.
