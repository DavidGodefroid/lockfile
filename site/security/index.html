Security model

The rule: the agent only ever sees 1s and 0s about a file.

The human approves every plan in a console the agent cannot drive, in an account the agent cannot read. Skills, rules and MCP tool descriptions only guide the agent; the console’s checks are the guarantee. This page summarises the full security model.

Boundaries

Boundaries and what enforces them

Residual: whoever runs docker commands can attach or exec into it (what Docker does and does not separate)

A plugin cannot read anything but its input, nor talk to the networkLandlock (execute and read its own binary only; TCP denied with ABI ≥ 4), seccomp (no sockets, ptrace, mount, bpf, keyctl, execveat and memfd_create (only its own binary executes, by Landlock), System V IPC, POSIX message queues, signals to other processes including through a descriptor owner, shared anonymous memory), rlimits, empty environment, input as a read-only fd 3, stdout capped at 3 bytes, stderr discarded; no other account in the console’s pid namespace sees the plugins’ processes in /proc (see the sandbox hardening)

What the agent can see: the exhaustive list

Everything the console sends to the client (socket, CLI, MCP) is one of these, from closed lists. The end-to-end tests walk every response of every method against this list.

Everything the agent can receive
OutputWhy it is not file information
plugin answer 1 / 0the one allowed thing
result: null + plugin_errorabsence of an answer; residual: it depends on the file (a plugin failed on it); at most one symbol per plugin, capped by max_plugins_per_handle
fetch_failedthe plan could not start; residual: says “this key could not be fetched” (missing, too big, denied and network are not distinguished)
handle f_…, plan id pl_…random, from crypto/rand
plugin name, version, official, warning: unofficial_marketplace, question, meaning of 1/0plugin metadata from the signed manifest
profile names and production flag, busylockfile configuration; busy means the console is waiting for the human on another request
approval_denied, approval_timeouta human decision; the reason the human types is never forwarded
refusal codes (E_*, with a static hint)computed from the request and the local install, before or without reading the file
status: console up, production, auto mode, security level, timers, plugin protocol, sandbox okconsole state

Never sent: size, media type, sha256, key listings, file or path names, page or byte counts, library or OS error text, per-plugin timing, progress during a run, stderr. The client also refuses to forward any console text it does not recognise: an unknown error becomes console error.

Side channels

  • Timing. A run’s response leaves the console only at the next multiple of answer_quantum (default 5 s) after the run started; a fetch failure after approval too. Residual: a plan that takes longer than one quantum shows it took longer.
  • The console window. At desktop security level 1 the agent’s account can read the console’s window. It shows the agent’s own request, the plugin metadata and the outcome codes; causes, sizes and hashes go to the audit only. Residual: the start-up lines show the profile’s location, and a reason you type with a denial (n <reason>) is echoed in the window: do not type file details there.
  • Exit codes depend on the outcome only, never on an answer.

Data at rest

  • Fetched files live in a random 0700 workspace in the console account, deleted on release, on handle expiry, on console exit, and swept at start. Deletion is an unlink, not a secure erase.
  • Credentials: the S3 SDK keeps the secret access key in the console’s memory for the session; core dumps are disabled.
  • The audit log (~lockfile/.local/state/lockfile/audit.log, 0600) is the one place file metadata exists: key, size, sha256, fetch cause, each plugin’s precise outcome, stderr byte count. Never file bytes. lockfile audit reads it, in the console account only.

Sandbox hardening (since v0.3.0)

“The agent only ever sees 1s and 0s” is the design goal and what the wire carries. A review of the v0.2.0 sandbox found side channels a plugin could use to pass more than its bit to another process on the machine. Since v0.3.0:

  • System V IPC (shm*, msg*, sem*) and POSIX message queues (mq_*) are denied to plugins by seccomp;
  • signals to any process but the plugin itself are denied, including through a descriptor owner (fcntl F_SETOWN/F_SETSIG, ioctl FIOSETOWN/SIOCSPGRP), whatever the Landlock ABI;
  • a running plugin’s /proc entries (command line, thread names, memory counters), which it writes itself, are kept from other accounts: the console runs plugins only where no other account can see their processes in /proc. On a host, /proc mounted with hidepid=invisible; in the release container, which Docker cannot mount so, a pid namespace of its own, not the host’s, that lists no process of an account other than root and the console’s, under a seccomp filter. Checked at start, when a plan arrives and just before it runs; refused otherwise (proc_not_hidden), and reported by lockfile doctor.

Residual: the host’s pid namespace lists every container’s processes, so the host’s own accounts can read a plugin’s entries unless the host’s /proc has hidepid=invisible. Whoever has Docker on the host is outside the boundary anyway.

Residual risks

  • A plugin whose code does not match its question (it lies, or answers a content question under a structural name) is mitigated by review, build from reviewed source, signing and the unofficial-marketplace warnings; it is not prevented.
  • Many plugins over one file combine bits: bounded by max_plugins_per_handle and by the per-plan approval that states how many answers the plan reveals.
  • A question can itself be about content (“is the amount above 10 000?”): the official marketplace’s review refuses such questions; an unofficial marketplace may not.
  • fetch_failed and plugin_error each carry one symbol that depends on the file.
  • Fetched files are unlinked, not securely erased (a residual on SSDs and copy-on-write filesystems).
  • Malware running as the console account, or as root, is out of scope.
