Install lockfile

lockfile runs in Docker. On your machine: Docker, one lockfile command (a launcher that runs every command in the signed release image, with the account it needs) and the seccomp profile of the console’s container.

The image holds the separated setup: the console as lockfile, the agent as agent in lockfile-clients, the socket directory shared through the lockfile-run volume, the console’s state in the lockfile-home volume. Its images are published for amd64 and arm64 and signed with cosign by lockfile’s release workflow.

Requirements

  • Docker on Linux, on a kernel with Landlock and seccomp, which sandbox the plugins (Landlock also denies TCP from kernel ABI 4). lockfile doctor reports what the kernel offers; without them, plans are refused with E_SANDBOX_UNAVAILABLE. On Windows, WSL 2 with Docker Desktop.
  • cosign on PATH, for the install script and lockfile update. Without it nothing is installed: there is no unsigned mode. The image has its own cosign for the plugins.

1. The launcher

V=vX.Y.Z
curl -fsSLO "https://raw.githubusercontent.com/DavidGodefroid/lockfile/$V/scripts/install.sh"
less install.sh                     # read it first
LOCKFILE_VERSION=$V sh install.sh

It checks the signatures of checksums.txt and of the images against lockfile’s release workflow run on that exact tag, then the archive against checksums.txt, and installs /usr/local/bin/lockfile and /usr/local/share/lockfile/seccomp.json, root-owned, with sudo if needed. The launcher runs the image by its verified digest. lockfile version prints the launcher’s and the image’s versions.

The launcher runs console as lockfile, confined under the seccomp profile; profile, plugin, marketplace, audit, forget and doctor as lockfile on its home volume; init and doctor --fix as you; the agent’s commands as agent with the socket volume only. What runs where.

2. A source profile (console account)

Profiles live in the lockfile account’s ~/.config/lockfile/config.toml; there is no per-project config. lockfile profile add appends one, validated:

# S3 (or an S3-compatible endpoint), credentials from Vault, production
lockfile profile add docs --source s3 --bucket documents --region eu-west-1 --prefix invoices/ \
  --credentials vault --vault-path secret/data/lockfile/docs --production

# SFTP with a key, host key checked against known_hosts
lockfile profile add partner --source sftp --host sftp.example.org --user reader --auth key \
  --key ~/.ssh/partner_ed25519 --known-hosts ~/.ssh/known_hosts --base-dir /outgoing

# A local directory, mounted read-only in the console's container
lockfile profile add samples --source local --path /srv/lockfile/samples
[profiles.docs]
source = "s3"                 # s3 | sftp | local
bucket = "documents"
region = "eu-west-1"
endpoint = ""                 # S3-compatible server; https:// (http:// only for localhost)
prefix = "invoices/"          # keys outside the prefix are refused
credentials = "vault"         # ask | keychain | vault
vault_path = "secret/data/lockfile/docs"
production = true             # the profile name is typed for every approval
max_object_bytes = "50MiB"    # larger objects are not fetched
max_plugins_per_handle = 16   # answers revealed about one fetched file, at most
handle_ttl = "30m"            # a fetched file is deleted after this
answer_quantum = "5s"         # results leave the console only on multiples of this

No file ever holds a secret: it is typed at console start (ask), read from the console account’s keychain, or read from Vault. lockfile forget --profile P deletes a keychain secret. The full list of keys is in the usage guide.

3. Plugins (console account)

lockfile plugin install file.non-empty@1.0.0     # exact versions only; signatures checked with cosign
lockfile plugin install format.is-pdf@1.0.0
lockfile plugin install pdf.parses@1.0.0
lockfile plugin list

The official marketplace’s signer is pinned in the binary. See Plugins for the catalogue, updates, unofficial marketplaces and how to write your own.

4. The console, with its hub

lox add lockfile samples
lox up
lox attach samples   # the policy review (detach: Ctrl-P Ctrl-Q)
lox approve          # the agent’s plans

The console runs attached to lockhub only: lockhub’s lox CLI declares the lock and starts it with its hub (lockfile console on its own refuses to start). It runs in a container of its own, under the shipped seccomp profile (never seccomp=unconfined), without capabilities, on a read-only root. It checks the isolation, asks for the secret, connects and serves the profile’s socket. Every plan waits for your approval on lockhub.

5. Wire your agent (your account)

lockfile init claude                # or codex, cursor, gemini; this project
lockfile init claude --user         # every project of this account
lockfile doctor --fix               # wires the installed agents not wired yet

lockfile mcp, the MCP command it writes, runs through the launcher in a throwaway container. Claude Code may call lockfile_status, lockfile_sources and lockfile_plugins without a prompt; plans and runs always go through Claude Code’s permission prompt and the console.

Upgrade

lockfile update [vX.Y.Z]

Checks the release’s and the image’s signatures as the install script does, replaces the launcher and the seccomp profile, then pulls the image. Restart the console afterwards; the volumes keep its state.

Build

docker build -t lockfile https://github.com/DavidGodefroid/lockfile.git
LOCKFILE_IMAGE=lockfile lockfile version

Your own image; from a clone, sh scripts/lockfile … runs it with the clone’s seccomp.json.
